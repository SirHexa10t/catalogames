Exact ids for games we only match by title (researched 2026-09-18, DEFERRED by the developer:
"maybe even more... but some other time. I'm hopeful that we'll come across some pre-indexed
source that'd save us the effort of data-mining"). Two halves, both blocked on the same wish:

    EPIC. An Epic library entry carries only Epic's own `app_name` (an opaque slug, 453 of 590
    are 32-hex) and a title. No Steam app-id, so ownership is matched by title and marked `?`.

        `app_name` resolves to NOTHING public. Established five ways: keyword search does not
        index launcher names; the catalog and launcher services are 401; there is no by-name
        query in the schema; and `releaseInfo.appId` EXISTS in the public schema and comes back
        empty in all 406 offers and items probed. Do not build against that field.

        The route that works, measured: title -> Epic's own searchStore -> pageSlug ->
        Wikidata P6278 -> P1733. Scored against recorded answers on 100 games: 87 correct,
        0 wrong, 13 no-match — and 7 of the 13 were the test feeding Wikidata labels rather than
        real titles, which we do not have to do. Precision was perfect; it fails by missing.
        Needs NO legendary re-run, no parser change and no schema change: our stored titles are
        already Epic's store titles (8 of Epic's 13 current giveaways are in the library and all
        8 matched exactly). Cost is ~590 keyword requests at generation time, batchable by
        GraphQL alias.

        Its ceiling is Wikidata's coverage, not the mechanism: ~445 of 590 (75%) of our titles
        reach an item carrying both properties, so about a quarter stay title-matched whatever we
        build. The misses are UNFILLED properties on items that exist, so the number drifts up on
        its own as editors fill P6278 — and Wikidata is CC0, so a committed table is permitted.

        Ambiguity, and it is small: 14 of 2,444 joinable slugs (0.6%) reach two Steam app-ids.
        Filtering to appdetails type == "game" collapses the two DLC cases; the other 12 are
        genuine pairs (GOTY vs base, remaster vs original, Red Dead Online vs RDR2) and one is
        simply a wrong P1733 upstream. The rule is: emit neither and report it ambiguous, as
        `crossover::ambiguous` already does. No tiebreak survives the set — lowest app-id picks
        the wrong game for hello-neighbor-hide-and-seek, newest picks Red Dead Online.

        Nothing else is committable. IGDB has the right shape and free access, and the Twitch
        agreement forbids redistribution outright with a 24-hour cache limit. PCGamingWiki
        carries both ids under CC BY-NC-SA — the NC alone rules it out for a crate that intends
        to publish. SteamGridDB is artwork keyed on store ids, not a crosswalk. Three GitHub
        searches for an existing Epic-to-Steam mapping returned nothing.

    STEAM. A `[owned on Steam?]` mark means we could not get an app-id for the game on sale, so
    its title was compared against the library's names. It happens because a store that publishes
    no app-id (Humble publishes none) can only be resolved through `steam_inventory`, which holds
    415 entries. Names are nearly unique — 4 of 2,282 normalised names reach two app-ids, 0.18%,
    and all four are GOTY/remaster/edition pairs — so the guess is usually right, and wrong in
    exactly the way that is hard to notice.

        The keyless bulk list is GONE: ISteamApps/GetAppList now answers "Method 'GetAppList' not
        found in interface 'ISteamApps'" on v1, v2 and v0002, with the rest of Steam reachable on
        the same probe. It is a withdrawn method, not a moved path, so it will not come back.


A local snapshot instead of a curated table (researched 2026-09-18, DEFERRED — the developer
wants "a big text file... queried at runtime", ms lookups instead of minutes at compile time):

    THE CATALOGUE IS CHEAP. IStoreBrowseService/GetItems/v1 is keyless, takes a JSON `input_json`
    of up to at least 150 app-ids per GET, and returns per item: both review summaries, platforms
    WITH steam_deck_compat_category, release as a UNIX TIMESTAMP, tags with VOTE WEIGHTS,
    developers, publishers, franchises, categories and content descriptors. Confirmed here: all
    415 committed entries fetched in 3 requests. A full 187,144-game sweep is roughly 1,250
    requests, about 20 minutes, JSON, no HTML parsing. It supersedes the store-search HTML route
    on every field except enumeration, for which IStoreService/GetAppList is 4 requests behind a
    Web API key with `if_modified_since` making refreshes nearly free.

    ONLY THE REVIEW BAND IS HARD, and the reason is the population this project chose. Valve's
    bulk surfaces expose exactly two summaries — `summary_language_specific` (english + steam)
    and `summary_filtered` (all languages + steam) — and NEITHER is `language=all` +
    `purchase_type=all`, which is what src/steam/store.rs asks for and what steam_inventory's
    house rules require, because key-activated copies are what a bundle catalogue is about. The
    all/all figure is exposed nowhere in the modern store API. It comes only from appreviews,
    per app.

        Measured here, our 415 committed entries against Valve's filtered band: 384 identical
        (92%), 26 a different band (6%), 5 where the filtered set has too few reviews to band at
        all. So adopting the filtered band is a 6% degradation, not a wholesale one — but a
        silent one, since every band would still look plausible.

        Also measured, and it sharpens a house rule: our all/all review COUNT is higher in 412 of
        415 (99%), while our approval PERCENTAGE is lower in 34%, higher in 24% and equal in 41%,
        mean -0.44 points. steam_inventory's "an entry here reads higher than the page" is true of
        the count and not of the percentage; worth wording precisely if that doc is ever revised.

        The way out is scope, not a better source: the band is only needed for the few hundred
        games a listing actually shows, not for 187,144. The catalogue comes from the bulk pass;
        the band comes from appreviews for what is on screen, which is what the program already
        does today and is well inside the documented 100,000-calls-a-day allowance.

    EPIC IS THE EASY HALF. searchStore pages at a hard cap of 40 per request; the category
    "games/edition/base" totals 7,008, so a full sweep is 176 requests (all 27,695 offers is
    693). Confirmed here: title, namespace and pageSlug come back on essentially every element
    (40/40 and 39/40 on the first page). Tags arrive as id AND name inline, so unlike Steam there
    is no 446-entry dictionary to join. There is NO review data at all — criticReviews,
    productRating and reviews are absent from the schema, not empty. Unreleased titles carry a
    SENTINEL release date of 2099-12-29T05:00:00.000Z rather than null, which will sort every
    unreleased game to the end of time if taken at face value.

        This is also what removes the privacy question: a bulk sweep plus a LOCAL title match
        needs no per-title queries, so nothing about anyone's library is ever sent to Epic.
        Prefer it over the per-title search route for that reason alone.

    NO THIRD-PARTY DATASET CARRIES THE BAND, at any population. SteamSpy gives raw positive and
    negative counts, from which Valve's tier cannot be reconstructed (the tier depends on the
    unrounded ratio AND the count), states no population, and carries no licence grant at all —
    only a bare copyright line — so it is fetch-yes, commit-no. steam-dataset-2025 stores about
    four individual reviews per app, not summaries, and is twenty months stale. The overriding
    point: a third party cannot license Valve's data, so a CC0 or MIT badge on a scraped dump is
    the uploader asserting rights over facts they collected.

    TERMS. Fetching to the user's own machine is EXPRESSLY LICENSED — Steam Web API Terms of Use
    section 2 permits distributing Steam Data "to end users for their personal use via your
    Application", and storage is contemplated with a disclosure-and-location condition rather
    than a time limit. THERE IS NO RETENTION OR CACHE CLAUSE ANYWHERE; the only deletion trigger
    is termination, which confirms copies are permitted while it stands. This is the clause that
    killed IGDB and Valve does not have one. Committing a derived file is outside the grant
    (section 9 reserves all rights not explicitly given), which costs nothing since the design
    wanted is the runtime one. The Subscriber Agreement's automation clause is about gameplay and
    accounts, not the storefront's JSON. Epic's terms address none of this at all — sixteen terms
    checked, all zero — so the Epic side is unaddressed rather than unsettled.

    ONE DECISION LEFT TO WHOEVER SHIPS IT, and the house already has a precedent for this shape.
    store.steampowered.com/robots.txt disallows nine specific paths and permits /api/,
    /appreviews/ and /search/. api.steampowered.com/robots.txt is "User-Agent: *" then
    "Disallow: /", complete. IStoreBrowseService/GetItems and IStoreService/GetTagList are on the
    disallowed host, while appdetails, appreviews and store search are on the permissive one.
    Note that src/bin/steam_tags.rs ALREADY fetches GetTagList from the disallowed host, so the
    question is not whether to start using it but whether one request becoming ~936 changes the
    character of access that already ships.

        This is the mirror image of the conflict src/discounted_sales/humble/mod.rs already documents — there the
        prose forbade while the machine-readable rules read as permission; here the machine-
        readable rule forbids while Valve's own section 2 expressly licenses. That module's
        answer was to state the conflict and leave the decision to whoever ships, and the same
        treatment fits here. The fallback if it goes the other way is characterised: the
        store-search HTML route on the permissive host, 1,872 requests, losing Deck, Metacritic
        and machine-readable dates.

    STILL UNMEASURED, and it needs the developer's own machine, no account:
        steamcmd +login anonymous +app_info_print 1867240 +quit
    That app's two populations are two bands apart, so review_score discriminates cleanly — 8
    means appinfo.vdf carries Valve's filtered figure and has the same defect as the store page,
    6 means it carries all/all and appinfo (one local file, every app, no crawl) answers the
    whole question. The prediction on file is 8, since every client-facing Valve surface uses the
    filtered population. Whether an anonymous sync populates a COMPLETE appinfo.vdf is the second
    half of the same check.

    All of it fits the existing generator pattern: a rarely-run tool behind the non-default
    `tools` feature, the way src/bin/steam_lookup.rs already does.

    Two findings worth having even if neither mapping is ever built, both from Epic's metadata:
    `mainGameItem` is present ONLY on DLC and names the parent — a structural DLC discriminator,
    where the Steam side has none and title heuristics were rejected after "ost" matched
    Ghostwire Tokyo and Samorost. And `ThirdPartyManagedApp` marks titles redeemed through Epic
    that need a Ubisoft or EA account to launch, which is arguably not "owned on Epic" in the
    sense a reader takes it.


Things the 30,000-row sweep taught (measured 2026-09-20, before widening further):

    THE SLICE IS HEAD-BIASED AND STATISTICS FROM IT WILL MISLEAD. The store's search orders by
    its own relevance, so the first N are the popular N. Over 30,000 games, review bands 2 and 3
    — Very Negative and Negative, which are the SAME percentage band as 1 but with fewer reviews
    — are completely empty, while band 1 has four real entries (C&C4 Tiberian Twilight at 16% of
    4,832; War of the Three Kingdoms at 10% of 82,111). Obscure, thinly-reviewed games simply
    have not been reached yet. Do not compute a distribution from a partial sweep and call it
    Steam.

    `incl` IS NOT A PARENT POINTER, and it was mis-described twice before anyone measured it.
    7,158 of 30,000 GAMES carry one, so it is not a supplementary-item field, and the relation
    runs in no consistent direction: app 10 names app 80 and app 80 names app 10 back, while app
    323180 (Portal 2 Soundtrack) names 620 and 620 names nothing at all. Read it as "these apps
    arrive together in one store item". Still the best lead toward a product-type column; not
    usable as a parent link without checking both directions.

    NAME HEURISTICS FIRE CORRECTLY AND ARE STILL WRONG, which is why they are reported and never
    acted on. Five names tripped the check in 30,000 and one of them is `DLC Quest` — a game
    whose title genuinely contains the word as a word. The rule did its job; the conclusion would
    have been wrong. Same class as "ost" inside Ghostwire Tokyo and Samorost.

    RATE LIMITING IS SURVIVABLE AT THIS SCALE. 300 search pages plus 200 item batches drew five
    HTTP 429s, every one cleared by the first 20-second backoff. Pacing at 1.5s held.

    SIZE: 30,000 rows is 4.6 MB, mean line 156 chars. The full 187,144 projects to about 29 MB,
    which git stores at roughly 40% of that and deltas to almost nothing on append.

    COVERAGE at 30,000: 99% carry a developer, 99.7% a publisher, every row has tags, and all
    30,000 app-ids are distinct — the enumeration dedup guard held across 300 pages. Deck:
    11,637 playable, 6,304 verified, 3,172 unsupported, 8,873 unknown.


Repair passes over the catalogue snapshot (noted 2026-09-20, for once the sweep is complete):

    The bulk endpoint leaves two kinds of hole, both small enough to repair one app at a time and
    far too large to fetch that way in the first place. `steam-issues.tsv` names every affected
    app, so a repair pass reads that file rather than re-sweeping.

    MISSING RELEASE DATES. `IStoreBrowseService/GetItems` returned no `steam_release_date` for 10
    of the first 10,000 — all long-released, heavily-reviewed games (Sleeping Dogs, Shogun 2,
    Mafia, Gothic), so "unreleased" is NOT the explanation; `appdetails` reports
    `coming_soon: false` for them. The repair:

        GET https://store.steampowered.com/api/appdetails?appids=<id>&filters=basic,release_date
        -> {"<id>":{"success":true,"data":{"release_date":{"coming_soon":false,"date":"28 Aug, 2002"}}}}

    Measured on three of them: Mafia yields `28 Aug, 2002` where the bulk endpoint had nothing,
    while Sleeping Dogs and Shogun 2 come back with `date: ""` — Valve genuinely publishes none.
    So the pass fixes some and confirms the rest as truly dateless. Note `appdetails` is on the
    permissive host, takes ONE appid per call for every filter except `price_overview`, and costs
    about 0.43s each — fine for tens of apps, impossible for tens of thousands.

    A SEARCH LINK INSTEAD OF A GAME PAGE. A Fanatical pack whose contents the store would not
    describe is now listed from the pack's own names, but those entries carry no Steam app-id, so
    `render::page_of` falls back to a search URL. The catalogue index is what fixes it, through a
    step not yet built: resolve the vendor's product NAME against the Steam name index to recover
    the app-id. That is the same title-matching machinery the Epic mapping needs, so one
    mechanism serves both.

    UNRESOLVED APPS. The store's search lists them and the item service returns `success: 0` with
    no record at all — delisted, region-locked or withdrawn (4 of the first 10,000: MONOPOLY
    Poker, FINAL FANTASY XI, AION MMO, Governor of Poker 3). They are written as a row of `?`
    so the file agrees with the store's own index, and `appdetails` is worth trying on them too.


Fields `GetItems` returns that the sweep does NOT yet ask for (noted 2026-09-20):

    The full response carries far more than the sweep requests. Everything below was confirmed by
    asking for every `data_request` flag at once on app 620. Worth revisiting when a column is
    wanted, since they cost nothing extra per request:

        basic_info            developers, publishers NOW FETCHED as names. short_description not.
                              Names rather than the creator_clan_account_id beside them: measured
                              over 100 games, 38% of developers and 16% of publishers carry no
                              clan id, so an id-and-dictionary scheme would lose a third of them.
        categories            controller_categoryids, feature_categoryids,
                              supported_player_categoryids  <- NOW FETCHED as the `feats` column,
                              the three arrays merged. IStoreBrowseService/GetStoreCategories/v1
                              is keyless and returns all 72 with names and kinds in ONE request —
                              the exact counterpart of GetTagList, written to steam-categories.tsv.
                              Two ids can share a name (30 and 51 are both "Steam Workshop", 55
                              and 56 both "DualShock Controller Support"), so it is an id->name
                              lookup and never the reverse.
        included_items        included_apps, included_bundles, included_packages
                              <- NOW FETCHED. Corrected from an earlier note that called this the
                              DLC-to-parent link outright: for a GAME it returns store packages,
                              which is purchasing trivia. `included_apps` is the parent link, and
                              it appears on SUPPLEMENTARY items — app 323180 (Portal 2 Soundtrack,
                              type 11) carries included_apps [620], and appdetails agrees with
                              fullgame {appid: 620}. A games-only sweep therefore sees it empty;
                              widening past category1=998 is what makes the column earn its place.
        type                  NOW FETCHED. Valve's own product kind: 0 game, 11 music. This is the
                              discriminator a product_type column would be built on, and storing
                              Valve's number rather than a private 0/1/2 keeps it reversible.
        best_purchase_option  final_price_in_cents, formatted_final_price, packageid,
                              included_game_count, must_purchase_as_set
        purchase_options      the same, one per edition — several per game
        package_groups        name
        supported_languages   NOW FETCHED as three base-36 bit masks over `elanguage`, one per
                              flag. They are NOT nested: measured over 3,683 rows, `supported`
                              holds for 3,676, `subtitles` 2,360, `full_audio` 1,348, and
                              `supported` is false 7 times, so none is derivable from another.
                              elanguage runs 0..=31, which fills a u32 EXACTLY — a 33rd language
                              overflows it, so the codec refuses one and raises
                              `language-out-of-range` rather than dropping it.
                              DROPPED: `eadditionallanguage`, the regional variant (Spanish-Spain
                              vs Spanish-LatAm) on 13.6% of rows, whose ids run past 54 and would
                              need a second wider mask per flag for a distinction nothing queries.
        assets                header, hero_capsule, library_capsule, page_background_path, …
        screenshots           all_ages_screenshots
        trailers              highlights, other_trailers
        full_description_bbcode
        tagids                the same ids as `tags`, without the weights
        platforms             steam_os_compat_category, steam_frame_compat_category,
                              steam_machine_compat_category  <- NOW FETCHED as the `compat`
                              column. Each is 0-3 like the Deck one, so three of them are exactly
                              six bits and exactly one base-64 digit with nothing wasted. Deck
                              keeps its own column: it is the one anyone reads by eye, and a
                              fourth field would spill into a second character.

    `tags` carries a WEIGHT per tag that the sweep still drops, DELIBERATELY. It is the vote count
    behind the ordering, and it would let a reader say how strongly a tag applies rather than only
    that it does — but it is the most expensive column measured: 52.2 ch/row raw, 8.48 MB over
    162,371 rows, more than everything else added put together. The ordering itself is free and
    already kept: the array arrives sorted descending by weight in 150 of 150 apps sampled, so
    position already encodes rank and only magnitude is missing. If it is ever wanted, store one
    absolute anchor plus 19 single-character ratios to it: 19.8 ch/row, 3.22 MB, 62% cheaper.

    STILL UNTAKEN, both measured, both cheap, neither chosen:
        content_descriptorids  mature-content flags on 37% of games — 1 nudity, 2 violence/gore,
                               3 adult-only, 4 frequent adult, 5 general mature. Five values fit
                               one base-36 character: 0.16 MB.
        basic_info.franchises  "Dota", "The Witcher", on 18% of games. 0.43 MB as names.

    BOTH RESOLVED 2026-09-25 by the union sweep; kept here for the reasoning. The resume offset is
    fixed (each country is walked from 0 under a stable sort, and finished countries are recorded
    with a `# done CC` line in the roster), and the shortfall is gone: Name_ASC took the catalogue
    from 162,371 to 188,310 in one country, and seven more countries added 140 games between them
    — JP 69, PL 23, ZA 12, IN 10, BR 10, IL 8, AU 8.

    AND TWO COUNTRIES ARE ENOUGH. Re-querying those 140 under 18 country codes: JP can describe 124
    of them, KR and SG 70 each, everything else fewer. CA + JP therefore covers 188,434 of 188,450,
    and 13 of the 16 it misses are reachable from no country at all — so the real miss is three
    games. Measured cost: 67 min per country enumeration (1,885 pages at 2.13 s), 56 min to
    describe 188,450 apps, 10.2 h for the eight-country run against about 3.3 h for CA + JP. The
    full table is in the module docs of src/store_inventory/steam/mod.rs; the sweep still defaults
    to eight because that is what produced the committed snapshot.

    WHAT REMAINS UNRESOLVABLE, measured: 13 apps of 188,450 that the search listed during
    enumeration and that NO country would describe afterwards — 18 country codes tried, plus
    appdetails, all refusing. They are not a defect in the sweep. A full sweep takes hours, and an
    app unpublished inside that window is listed by the phase that ran first and gone by the phase
    that ran second. The only way to shrink it is to shorten the gap.

    TWO OPEN FAULTS IN THE SWEEP ITSELF (found 2026-09-21, both since fixed — kept for the
    reasoning, since each needed a decision rather than a patch):

        Resume restarts at the wrong offset. `enumerate` resumes a part-written roster with
        `start = ids.len()`, but ids are DEDUPLICATED while the offset counts positions walked, so
        the two diverge and the run re-walks pages it already has. It self-corrects (duplicates are
        dropped) and cost about 88 seconds once, so the damage is time, never wrong data. A real
        fix has to persist the offset, and every place to put it is a tradeoff: a comment line
        interleaved through the roster (append-only, but scatters ~1,900 comments through 162,371
        lines), a sidecar file (clean, but a whole file for six bytes), or accept the re-walk on the
        grounds that the store's relevance order shifts between runs anyway, which makes an exact
        resume offset meaningless in the first place. That last reading is the reason this is not
        simply a bug: it may be right.

        Enumeration reaches 162,371 of the ~187,500 the store reports — 25,101 short. MEASURED
        2026-09-22, and it is neither delisting nor region-locking:

          - The sweep does NOT stop early. It walked to offset 187,592, past the reported total,
            and got an empty page. ~187,600 slots yielded 162,371 unique ids.
          - THE RELEVANCE ORDER IS NOT STABLE FOR EVEN A MINUTE. The same offset fetched twice
            40 seconds apart returned 0 of 100 identical positions and not even the same SET.
            `sort_by=Name_ASC` at the same offset returned all 100 identical, in order. Paging by
            offset over a continuously reshuffled ranking samples a moving target, so slots are
            spent on rows already seen while others are never surfaced.
          - Locally the pages are clean — 5 consecutive pages gave 500 distinct ids at offsets 0,
            60k and 120k — so the loss is not adjacent-page overlap. It accumulates across the
            48-minute walk.
          - The missing ids are REAL AND LIVE. 150 sampled from a Name_ASC walk that the roster
            lacks all resolved with success=1 (a delisted app fails there). Mostly obscure —
            median 1 review, 67 of 150 with none — but not junk: app 270550, Yet Another Zombie
            Defense, has 12,391 reviews. They are visible from the same machine that ran the
            sweep, so they are not region-locked either.
          - A Name_ASC sample of 18 pages found 13.2% of its ids absent from the roster, which
            extrapolates to ~24,700 over 187,510 — the observed 25,101 to within 1.6%.

        THE FIX IS `sort_by=Name_ASC` ON THE ENUMERATION URL, and it is free. The alternative,
        IStoreService/GetAppList, is authoritative in four requests but needs a Web API key the
        tool would then have to hold. (`Released_ASC` is silently ignored by the store; Name_ASC
        genuinely reorders.) Caveat worth checking on the first full run: games sharing a name
        have no defined tiebreak, so a handful may still shuffle.

        SEPARATE FINDING, REPRODUCIBILITY: the enumeration URL passes no `cc`, so the store
        geolocates the machine and the snapshot is implicitly scoped to wherever the sweep ran —
        nothing in the file records which. Measured on one stable Name_ASC page: no `cc` was
        byte-identical to cc=IL, while cc=US totalled 187,569, cc=JP 187,302, cc=RU 183,316 and
        cc=DE only 156,893 — 30,618 fewer games, an entirely different page. Two operators would
        therefore produce materially different files from the same command and no way to tell.
        Passing an explicit `cc` and naming it in the header would fix that; which country is the
        developer's call, since it decides what the snapshot is a snapshot OF.

        CAN WE GET ALL GAMES, FOR ANY COUNTRY? MEASURED 2026-09-23. Yes, and WITHOUT unioning
        several countries' enumerations — one sweep from a permissive country is enough:

          - There is no keyless global list to fall back on. ISteamApps/GetAppList 404s on both
            v1 and v2, confirming the earlier note.
          - Totals over 22 country codes: CA 188,169 (highest), MX 188,168, US 188,164, PL
            188,161, SE 188,160, GB 188,156 … then a cliff: RU 183,908, CN 177,744, DE 157,474.
            The top SIXTEEN are within 65 of each other, so "most permissive" is a tier, not one
            country, and which of them is highest will vary run to run.
          - THE RESTRICTED COUNTRIES ADD NOTHING. 800 app-ids listed by JP, RU, DE and CN — 200
            each, taken from their own Name_ASC pages — were ALL visible under CA. The censored
            catalogues are strict subsets, which is what censorship means and is worth having
            measured rather than assumed.
          - The top tier barely differs at all. CA and MX, whose totals differ by 1, showed 14
            apparent differences over a 400-id window; 13 were the window sliding a few positions
            alphabetically (CA had "Mad*" titles, MX "Lux*") and exactly ONE was a real regional
            exclusion — 2987800, Madoka Magica Magia Exedra, in CA and not MX. It is visible in
            CA, so a CA sweep catches it.

        SO: enumerate once, with `sort_by=Name_ASC&cc=CA` (or any of the top tier), and the id
        universe is essentially complete. Unioning a second country would double the enumeration
        cost to gain a handful of rows.
        CORRECTION, 2026-09-24: "essentially complete from one country" IS WRONG, and the 25
        `unresolved` rows are the counter-example. Those apps were enumerated by an IL-geolocated
        search and then refused by an item service asked as `US`. Re-queried: 0 of 25 resolve
        under US, 6 under CA, 18 under DE, 18 under JP, and ALL 25 under IL. So 19 games visible
        in IL are invisible in CA — CA is not a superset of IL, and the earlier conclusion was
        drawn from a test that only ever compared JP, RU, DE and CN AGAINST CA, never the reverse.
        Countries differ in BOTH directions; the developer's instinct that a union would be needed
        was right and the advice against it was not.

        What one country does buy is CONSISTENCY: whichever is chosen, using it for both the
        enumeration and the description means nothing is listed and then refused, which is what
        drives `unresolved` to zero. Completeness across countries is a separate, unfinished
        question, and its cost is one enumeration per country unioned.

        PER-COUNTRY AVAILABILITY IS A SEPARATE AXIS, and it does not need a second enumeration:
        GetItems takes `country_code` and reports `visible` per app. Measured over 150 roster ids
        — US 150/150 visible, JP 150, IL 150, RU 146, DE 133. If the program should say "you
        cannot buy this where you are", the cheap shape is a bitmask column over the few countries

Classifying Steam ids the tables do not hold (found 2026-09-29 while fixing bundle links; BUILT
2026-09-29 as `steam::items`, gate phase4-classify):

    Fanatical publishes Steam BUNDLE ids in `steam_id` — Iceborne Digital Deluxe carries 13009,
    which is /bundle/13009, and /app/13009 bounces to the store front. `inventory::steam::
    identity_of` says how far a published id is trusted (App / Unheld / Disputed / Unknown), and
    `sales` makes ONE batched IStoreBrowseService/GetItems request per run for the unheld and
    disputed ids, each asked as every kind it could be; `render::page_of(game, &classified)` then
    links a found id to Steam's own store_url_path, an id nothing claims to a search, and an id
    never asked (offline, a failed request, a library caller) exactly as before. A failure, an
    unanswered id and an id claimed by two kinds are all said above the listing.

    SIX TRAPS, all measured (fixture tests/fixtures/steam/getitems-13009-4278390-620.json):
      - `success` is an EResult (1 success, 15 refusal), never a boolean; a FAILED probe still
        answers with a path built from the id alone (`app/0/`, `bundle/620/`), so the path's
        shape is no signal — only `success == 1 && visible` is.
      - an id can be several things at once: 620 is app 620 (Portal 2) AND package 620 ("18
        Wheels of Steel", whose path is app/12520/…). Every claim is kept; the store's title
        picks by NAME (same_title against the claim's name), precedence app > bundle > package
        only breaks ties; collisions are reported as a note.
      - a package resolves to an APP's page, so the path is emitted verbatim, never `/sub/<id>`
        built from the kind — and re-encoded on the way out (it is external text in a shell
        script's URL).
      - a removed app fails all three probes: a class of its own, linked as a search, not a bad
        id. "Asked and nothing claims it" is kept apart from "never asked".
      - an ask the service leaves out leaves the id UNASKED (today's link), never "nothing".
      - the cap is the encoded request's LENGTH, answered with HTTP 400 (200 asks fine, 500
        refused), not truncation: BATCH = 150 asks (entries, not ids — an unheld id spends 3),
        and a 400 splits the chunk and retries.
    Also measured earlier: `/app/<id>` bouncing has three causes (removed, superseded — 34330 →
    /app/201270 — and the age gate), so a redirect is never the classifier; and a single-id
    `appdetails` request can answer keyed under a different app-id.

    The request names one country (US): a title unsold there is classified as nothing and gets
    a search link. Rare; the sweep, which needs the app itself, asks per country instead.
